## 2. 발견 (Findings)

### F1. [합의 · Major · 신뢰도:높] — Action: Modify

**발견:** 인덱스 전환은 필요하다. 형태는 "진입 인덱스 → 문서군 INDEX → 본문" 3단, 핵심은 파일 분할보다 **현재 유효한 상태를 좁히는 것**(활성·이력 분리). 큰 문서(DECISIONS·REMAINING·WORKLOG)만 분할·보관하고, 작은 문서(PLAN·LESSONS·NORTHSTAR·골)는 진입 인덱스의 같은 형식 줄로 노출하다가 임계값을 넘으면 전환.

**근거:** 데이터(DECISIONS 7.5만 자, REMAINING 완료 잔존 52%) + 패턴. Claude R1 F1과 GPT R1 발견 1이 같은 결론, R2에서 GPT가 "공통 인터페이스로 통일하되 큰 문서만 분할에 동의".

> **트레이드오프:** 즉시 보이는 과거 맥락이 줄고, 인덱스 갱신 비용과 위치 변경(링크·습관)이 생긴다.
> **검증:** 이전 전후 세션 시작 읽기량(자 수), 서브에이전트가 인덱스만 보고 관련 결정을 고르는지.

### F2. [이견 · Major · 신뢰도:중] — Action: Investigate

**발견:** 세션 시작 읽기 상한의 숫자.

**근거:** 추정. 양측 모두 근거 없는 초기값임을 R2에서 인정.

> **트레이드오프:** 낮게 잡으면 필요한 활성 정보가 하위 인덱스로 밀려 한 번 더 열어야 하고, 높게 잡으면 전환 효과가 준다.
> **검증:** 이전 후 실측 + 유형별 서브에이전트가 상한 안에서 필요한 줄을 찾는지.
> **GPT 입장:** 진입점 + 문서군 인덱스 합 약 3,000토큰. 초과하면 잘라 읽지 말고 보관·하위 인덱스로 내린다. 골 결정 후 본문 읽기는 별도 측정. 검증된 최적값은 아님(R2에서 고수하지 않겠다고 함).
> **Claude 입장:** 3,000토큰(한국어 약 4~6천 자)은 DECISIONS 활성 INDEX(106줄 × 약 80자)도 못 담는다. 진입 + 활성 INDEX + REMAINING 활성 + NORTHSTAR ≈ 1.2~1.5만 자, 상한 초과 시 하위 인덱스로 내리고 lint 경고. 역시 실측으로 조정할 운영값.
> **이견 출처:** 증거부족
> **→ 사용자 판단 필요**

### F3. [이견 · Major · 신뢰도:중] — Action: Investigate

**발견:** 인덱스 유지 방식 — 손 추가 + union + lint vs 생성형.

**근거:** 패턴 + 추정.

> **트레이드오프:** 손 추가는 누락·정렬 충돌, 생성형은 브랜치별 재생성 충돌·원본 규칙 필요.
> **검증:** 2인 e2e에서 같은 날 두 브랜치가 같은 INDEX에 줄을 추가하고 머지할 때 충돌률.
> **Claude 입장:** 생성형은 브랜치마다 다시 만든 파일이 머지 때 충돌한다. 손 추가(append-only) + union + lint(본문엔 있는데 INDEX에 없음·끊긴 링크) + check-record(같은 커밋에 INDEX 줄)가 팀 병행에 맞다.
> **GPT 입장:** 이 구도는 단정적이다. 수동도 정렬·상태 수정에서 충돌하고, 생성형도 결정적 생성 규칙이면 관리 가능. 특히 **이력(추가만)과 활성 목록(완료 제거·상태 갱신)은 갱신 방식이 달라야** 하므로 append-only + union을 전체 기본 정책으로 쓰는 데 반대.
> **이견 출처:** 증거부족
> **→ 사용자 판단 필요**

### F4. [이견 · Major · 신뢰도:중] — Action: Add(Claude) / Defer(GPT)

**발견:** 결정 번호(D-nnn) 원격 원자 예약(`refs/vibe-ids/D-nnn` push, 이미 있으면 거부).

**근거:** 패턴(독립 복제본이 아직 푸시하지 않은 로컬 커밋은 브랜치 스캔에 안 보임) + 추정.

> **트레이드오프:** 원격 쓰기·네트워크 의존, 예약 실패·방치 처리. 대신 독립 복제본 간 번호 중복을 원천 차단.
> **검증:** 2인 e2e에서 두 세션이 같은 날 결정을 기록할 때 번호 중복 여부(스캔만 / 원격 예약).
> **Claude 입장:** 같은 날 두 세션이 D-107을 동시에 쓰는 것이 인덱스 전환에서 가장 실제적인 충돌 지점이다. 브랜치 스캔은 아직 푸시 안 된 커밋을 못 본다. 원격 ref 하나로 원자적으로 막을 수 있고, 팀원은 이미 브랜치 push 권한이 있다.
> **GPT 입장:** 충돌 빈도와 순차 번호의 필수성이 확인되지 않았다. 원격 쓰기·네트워크·방치 예약이라는 운영 부담이 생긴다. 충돌 가능성 낮은 ID와 표시 번호 분리 등을 먼저 비교하고, 중앙 예약이 필요한 조건을 확인한 뒤 도입해야 한다(Defer).
> **이견 출처:** 가치
> **→ 사용자 판단 필요**

### F5. [합의 · Major · 신뢰도:높] — Action: Strengthen

**발견:** 사용자가 판정한 규칙(골 ID·Codex 골 판정 완료·리뷰 최대 3라운드·리뷰·QA 분리·UI 변경 시 Aside 증거·우회는 사용자 직접·기록 같은 커밋)은 **전부 기계 강제로 그대로 둔다.** 재분류(경고·설정·LLM 판단)는 그 밖의 규칙에만 한다.

**근거:** 가정(goal.md 하지 말 것). Claude R1 F4의 "불변식 6개만 기계 강제"가 확정 규칙 일부를 명시하지 않아 약화 위험이 있다는 GPT R2 지적을 Claude가 수용(이 통합에서). 골 ID 존재와 Codex 판정 완료는 서로 다른 조건이라는 지적도 포함.

> **트레이드오프:** 기계 강제 목록이 길어져 "가벼운 구조" 체감은 줄어든다.
> **검증:** flexibility.md 표에서 확정 규칙 행이 전부 "기계 강제"인지, 기존 테스트가 그대로 통과하는지.

### F6. [합의 · Major · 신뢰도:중] — Action: Reframe

**발견:** 경직성의 원인은 파이썬 사용이 아니라 "무엇을 판정하게 했나". 관측 가능한 불변식은 스크립트로, 의미 판단(유사도·크기 적절성·설계 타당성·디자인시스템 준수·충돌 해석)은 LLM으로, 저장소 정책(접두사·글롭·테스트 명령·임계값·제목 이름)은 설정으로. 모든 차단 메시지에 다음 준수 경로를 함께 출력한다.

**근거:** 패턴. Claude R1 F4, GPT R1 발견 3이 같은 결론. GPT R2는 제목 파싱을 설정으로 빼는 것만으론 형식 취약성이 해결되지 않으니 안정된 표식도 비교하라고 보탬.

> **트레이드오프:** 통과/실패보다 판정 근거·상태 표현이 복잡해진다.
> **검증:** 기존 차단 사례를 실제 위반·오탐·정보 부족으로 분류, 오탐 집중 의미 판정부터 이동. 설정 키 전환 후 기존 테스트 통과.

### F8. [이견 · Major · 신뢰도:중] — Action: Split

**발견:** 세부 스킬 분리 범위 — 개발 단계를 스킬로 둘 것인가.

**근거:** 패턴 + 추정. 양측 모두 "오케스트레이터 유지 + 단계 스킬 분리 + 규칙 원천 하나 + 직접 호출도 같은 게이트"에는 합의.

> **트레이드오프:** 스킬이 늘면 설명이 매 세션 목록에 실리고 발동 경쟁이 생긴다. 줄이면 사용자가 원한 "프론트·백엔드 개발만 부르기"가 프로필 지시로만 가능.
> **검증:** 단독 호출·전체 호출 서브에이전트 시험 + 오발동 시험(구현 요청에 리뷰 스킬이 뜨는지).
> **Claude 입장:** 게이트와 1:1인 다섯(선점·설계 확인·리뷰·QA·기록) + 오케스트레이터. 개발은 게이트가 아니라 일하는 방식이라 진입 조건·산출물 검사가 없고 "구현할 때"로 발동이 겹친다 → 프로필 문서. R2에서 사용자 예시를 보면 "개발 스킬 = 얇은 진입점 + 프로필 선택"이 의도에 더 맞을 수 있다고 인정.
> **GPT 입장:** 총 7개(오케스트레이터·선점·설계·개발·리뷰·QA·기록). 프론트·백엔드는 개발 스킬의 참조 지침. 분리 기준은 게이트 존재가 아니라 **독립 호출 수요와 고유한 실행 지침**. Claude의 다섯 단계안은 유력 후보이지 확정 답은 아님(R2).
> **이견 출처:** 가치
> **→ 사용자 판단 필요**

## 4. 권고 (Recommendation)
