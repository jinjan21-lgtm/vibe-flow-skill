# 신규 프로세스 결정 (2026-10-17)

구조도·충돌 분석·사례 조사·사용자 중간 요청에서 나온 후보를 하나씩 판단했다. 기준은 세 가지다. 바이브코딩의 핵심 위험(범위 자기 확장, 완료 자기 판정)을 줄이는가. 사용자가 판정한 규칙과 부딪히지 않는가. 비용 대비 효과가 지금 확인되는가.

## 결론: 새 스킬은 만들지 않는다

> 3차 결정 D36에서 바뀜 — 새 **단계**는 만들지 않되, 기존 단계를 따로 부를 수 있는 세부 스킬로 나눴다(아래).

모든 채택 항목은 vibe-flow의 기존 단계 안에 들어간다. 새 단계를 만들면 상태 전환이 늘고 우회 지점이 생긴다. 디자인시스템도 별도 스킬이 아니라 "UI 파일이 바뀔 때의 입력"으로 넣었다.

### D36 단일 vibe-flow vs 단계별 세부 스킬

| 기준 | 단일 vibe-flow (런 2까지) | 세부 스킬 + 오케스트레이터 (채택) |
|---|---|---|
| "리뷰만", "QA만", "프론트만" 같은 부분 호출 | 스킬 전체를 읽고 해당 행을 찾아야 함. 단계 진입 조건은 스킬 본문의 흐름 표에만 있음 | 그 단계 스킬이 바로 뜨고, 첫 줄이 진입 조건 검사(`mr_check --stage`) |
| 전체 자동 진행 | 한 스킬이 순서를 들고 있음 | 오케스트레이터가 `mr_check --next`로 지금 단계를 찾아 세부 스킬을 차례로 |
| 규칙 원천 | 하나 | 하나 유지 — 세부 스킬은 얇게, 상세는 vibe-flow 폴더 문서(review-loop·qa-gate·structure) 참조만 |
| 매 세션 스킬 목록 비용 | 설명 1개 | 설명 7개(각 300자 안팎) |
| 발동 경쟁 | 없음 | 있음 — 설명을 "언제 쓰나"만, 단계별 사용자 말로 구분. 오발동 시험으로 확인 |
| 단계 생략 위험 | 흐름 표를 건너뛸 수 있음 | 진입점이 여러 개 — 각 스킬이 진입 조건을 검사해 **진입점이 늘어도 생략 권한은 생기지 않게** |
