# 개발 태스크 유형 매트릭스

**유형은 절차를 바꾸지 않는다.** 모든 유형이 같은 흐름(선점 → 설계 → 설계 확인 → 구현 → 리뷰 → QA → 기록)을 탄다. 유형은 ① 어떤 프로필을 읽고 ② 어떤 인덱스를 찾아 ③ QA에서 무엇을 확인하는지만 고른다. 유형은 겹친다(긴급 + 버그 + 풀스택) — 그때는 해당 줄을 모두 적용한다. 근거: [논의](debates/2026-10-17-handoff-index-skills.md) F12.

## 영향 표식 (MR 「영향·위험」에 적는다 — 검사를 고르는 실제 기준)

| 표식 | 뜻 | 따라오는 것 |
|---|---|---|
| `UI` | 화면에 보이는 것이 바뀐다(글롭 밖 헬퍼·i18n·목업 포함) | frontend 프로필 · 디자인시스템 · 브라우저 QA(Aside) |
| `API` | 요청·응답·오류 형식이 바뀐다 | backend 프로필 · 계약 테스트 · 호출하는 화면 확인 |
| `데이터` | 스키마·마이그레이션·저장 형식 | 되돌리기 경로 · 리뷰 blocker 기준(손상·유실) |
| `의존성` | 패키지·런타임·빌드 설정 | 전체 테스트 · 잠금 파일 diff · 빌드 산출물 확인 |
| `긴급` | 운영 장애·마감 | 게이트 면제 없음. 크기가 작으면 설계 확인 생략 기준을 쓸 수 있고, 후속 골 후보를 남긴다 |

## 강도 프로필 (위험 기반 — mr_check가 MR에서 판정)

| 프로필 | 조건 | 따라오는 것 |
|---|---|---|
| 경량 | 「영향·위험」 `- 위험:`과 「설계」 `데이터·API 변경:`이 둘 다 정확히 `없음` | 작으면(`design_skip` 기준 이하) 설계 확인 생략 가능. 리뷰는 1라운드로 끝나는 것을 기대(지적이 나오면 규칙대로 2·3라운드) |
| 표준 | 그 밖의 위험 표식 | 설계 확인 생략 불가. merge에 RED 증거 — 이 브랜치의 `.vibe/qa/red-<tree>.json`(`qa_run.py --red --mr <MR>`, exit≠0, 이 골·지금 기준)에서 실패한 테스트 하나 이상이 QA 기록 `tests`에서 `ok`(RED·QA 모두 테스트별 결과가 있어야 — test_cmd는 상세 출력 `-v`. RED는 QA보다 먼저 돈 것만). 리뷰 라운드 1 CHECKED 근거는 조건마다 실재하는 테스트 이름(경량은 `파일:줄`도 됨) — merge가 그 테스트를 QA 기록에서 대조. 나머지는 기본 흐름 |
| 강화 | 위 두 줄에 금액·결제·권한·인증·개인정보·삭제·마이그레이션·외부 API 계약 | 표준 + 「검증 계획」 `- 코드:`에 회귀 테스트 식별자(`test_x`·`Class.test_x`·`tests/x.py::name`·`tests/…py`, draft부터) + 「QA 결과」 `- 회귀: <돌린 테스트 식별자>`(줄 여럿 가능 — JS 테스트는 한 줄에 하나)(merge — 식별자마다 레포 테스트 파일에 있고, QA 기록 `.vibe/qa/<tree>.json` `tests`에 같은 이름(맨 이름은 마지막 성분, `Class.test_x`·`path::test_x`는 기록 이름 끝이 그 한정형)이 모두 `ok`여야. `tests`가 없으면 실행 증거 없음 — test_cmd를 상세 출력(`-v`)으로 qa_run) |

`없음(…설명…)`은 없음이 아니다 — 설명이 있으면 위험 표식이다. `--stage review`가 지금 프로필을 한 줄로 알린다.

## 유형별

| 유형 | 쓰는 단계 (세부 스킬) | 생략할 수 있는 것 | 찾아 읽는 인덱스 | 기록 위치 | 검증 |
|---|---|---|---|---|---|
| 프론트엔드 기능 | claim → design → dev(frontend) → review → qa → record | 없음 | 결정 `#화면ID` · WORKLOG 같은 토픽 · design-system | WORKLOG 토픽 + INDEX · REMAINING `[x]` · (결정 시) DECISIONS | 렌더·상호작용 테스트(없으면 문법 검사) + **Aside 역할별 캡처** |
| 백엔드 API | claim → design → dev(backend) → review → qa → record | 브라우저 QA — `해당 없음 — <화면 호출 없음 이유>`일 때만 | 결정 `#모듈·화면ID`(권한·금액·데이터 원천) · API 계약 | 같음 | 계약·권한 테스트(허용·거부) + 전체 테스트 |
| 풀스택 | claim → design → dev(fullstack) → review → qa → record | 없음 | 위 둘 | 같음 | 계약 테스트 → 서버 → 화면, Aside에 서버 오류 표시 시나리오 |
| 버그 수정 | claim(새 골, 또는 지금 골의 완료 조건이면 그 MR) → design → dev → review → qa → record | 설계 확인 — 작은 변경(기본 50줄·3파일)이면 `생략: 작은 변경` | 결정에서 그 동작을 정한 줄 · WORKLOG에서 그 기능 항목 | 같음 + 2회 이상 같은 원인이면 LESSONS | **재현 테스트가 먼저 실패**하는 것 확인 → 고친 뒤 통과. UI면 Aside |
| 리팩터링 | claim(골 필요 — G-000 범위 아님) → design → dev → review → qa → record | 없음(작으면 설계 확인 생략 기준) | 결정 중 구조·모듈 규칙 · LESSONS | 같음 | 동작 불변: 기존 테스트 전부 통과, 「계획 vs 실제」에 바뀐 구조. UI 파일이 바뀌면 Aside로 회귀 확인 |
| 긴급 수정 | 같은 흐름(게이트 면제 없음) | 작으면 설계 확인 생략. 리뷰 3라운드·QA는 그대로 | REMAINING 결정 대기·보류 · 관련 결정 | 같음 + REMAINING에 후속 골 후보(근본 원인) | 재현 테스트 + 전체 테스트, UI면 Aside. 우회가 필요하면 사용자가 직접, REMAINING에 부채 |
| 설정·의존성 변경 | claim(골 필요 — G-000은 의존성·설정 제외) → design → dev → review → qa → record | 브라우저 QA — 빌드·화면에 닿지 않을 때 이유와 함께 | 결정 중 런타임·도구 결정 · LESSONS(환경 교훈) | 같음 | 전체 테스트 · 잠금 파일 diff를 리뷰 입력에 · 빌드가 있으면 빌드 산출물 |
| 테스트 보강 | claim(골 필요 — 이름 정리만이면 G-000) → design(작으면 생략) → dev → review → qa → record | 브라우저 QA — `해당 없음 — 테스트만` | 완료 조건을 정한 골·결정 | 같음 | 새 테스트가 **고의로 깬 구현에서 실패**하는 것 확인(뮤테이션 1회) + 전체 테스트 |

## 세부 스킬을 따로 부를 때

| 사용자 말 | 부르는 스킬 | 그 스킬이 먼저 확인하는 것 |
|---|---|---|
| "다음 일 뭐야", "이거 집어" | vibe-claim | (없음 — 시작점) |
| "설계만 먼저" | vibe-design | `--stage claim` |
| "프론트만 붙여줘", "API만" | vibe-dev | `--stage build` |
| "리뷰만 돌려줘" | vibe-review | `--stage review` |
| "QA만" | vibe-qa | `--stage qa` |
| "기록해", "결정 남겨" | vibe-record | 골 작업이면 QA 결과 |
| "끝까지 해줘", 전체 | vibe-flow | `mr_check --next`로 지금 단계를 찾아 위 스킬을 차례로 |

진입 조건이 안 맞으면 세부 스킬은 일을 하지 않고, 맞는 단계를 알려 준다 — **호출 진입점이 여러 개라고 단계 생략 권한이 생기지 않는다.**
