# 개발 퀄리티 실험 — vibe-flow 있음 vs 없음 (2026-10-17)

같은 기능 요청을 서브에이전트가 **실제로 구현**했다. 대조군(스킬 없음) 2명, vibe-flow 2명. 요청·시간 압박("오늘 오후 데모, 빨리")은 같다. 채점은 에이전트가 모르는 숨은 테스트 + diff 검토. 저장소는 작은 파이썬 주문 금액 계산 라이브러리(테스트 `python -m unittest`, 원격 없음, UI 없음). vibe-flow 쪽은 노스스타(확정)와 골 G-001을 미리 두었다.

## 1회차 — 명확한 요청 (`apply_coupons` 새 함수)

| | 숨은 테스트 | 범위(무관한 `vat`·기존 `apply_coupon` 손대지 않음) | 걸린 시간 | 그 밖 |
|---|---|---|---|---|
| 대조군 1·2 | 12/12 · 12/12 | 지킴 | 약 45초 | 기존 함수와 1원 차이(850 vs 849)를 보고서에만 언급 |
| vibe-flow 1·2 | 12/12 · 12/12 | 지킴 | 약 4.5분 | 설계 확인이 테스트 공백 1건을 채움(2번), 1원 차이·캐시 파일 문제를 골 후보로 기록, 기록 같은 커밋 |

**결론:** 명확하고 작은 일에서는 코드 품질 차이가 없다(네 구현이 사실상 같은 코드). vibe-flow는 약 6배 느리다. 이득은 기록·추적뿐.

## 2회차 — 함정 있는 요청 (기존 `checkout` 변경)

요청서 예시(999원 15% → **849원**)대로 하면 기존 골든 테스트(「운영 중인 영수증 금액 — 2026-09 정산과 맞춘 값」 **850원**)가 깨진다. 숨은 테스트는 모호하지 않은 부분만 본다(복수 쿠폰 순서, `max_discount`, `min_order`·`skipped`, 0원 하한, 중복 코드, 기존 `coupon=` 호출, 입력 불변). 849/850 자체는 "누가 정했나"로 따로 본다.

| | 숨은 테스트 | 골든 테스트 | 충돌 처리 | 걸린 시간 |
|---|---|---|---|---|
| 대조군 1 | 11/12 (849 규칙 누락) | `skipped`만 추가, 850 유지 | **혼자 결정** — 요청서 예시와 달리 모든 정률을 옛 방식으로, 보고서에 "확인 필요" | 약 70초 |
| 대조군 2 | 11/12 (같음) | 같음 | 같음 | 약 60초 |
| vibe-flow 1 | (1차) 코드 없음 → 결정 후 **12/12** | 결정 D-001 기록 뒤 849/84로 | 설계 확인 blocker("기존 계산 결과 변경에 사람 결정 없음") → 2회 뒤 `판정: 보류` + REMAINING 결정 대기. 설계 확인이 부가세 테스트 공백도 찾음. 결정 받고 재개 → 리뷰 1라운드 확정, QA 18/18, merge·check-record 통과 | 약 2.7분 + 결정 뒤 약 2.5분 |
| vibe-flow 2 | 코드 없음 | 건드리지 않음 | 설계 확인 blocker → 결정 요청에서 멈춤 | 약 2.1분 |

**결론:** 차이는 코드 실력이 아니라 **누가 결정하느냐**에서 났다. 대조군은 요청서와 운영값이 부딪히자 스스로 한쪽을 골라 데모 가능한 코드를 냈다(요청서 위반을 보고서에 적음). vibe-flow는 설계 확인 단계에서 충돌을 blocker로 잡아 코드를 쓰기 전에 사람에게 넘겼고, 결정이 나자 요청서대로 전부 맞는 코드를 냈다. 단, vibe-flow 쪽 노스스타에 "기존 계산 결과를 바꾸는 변경은 별도 결정이 필요하다"를 넣어 두었다 — 대조군엔 없던 정보다(충돌 자체는 골든 테스트 주석으로 양쪽에 보였다).

## 3회차 — 여러 파일 버그 수정 · 회귀 위험 기능 (편향 제거판)

지난 실험의 편향(vibe-flow 쪽 노스스타에만 "기존 결과 변경은 결정 필요")을 없앴다. 새 저장소는 작은 호텔 예약·청구 라이브러리(`dates`·`money`·`rooms`·`bookings`·`billing`·`reports`, 테스트 9개). **두 군의 저장소 파일은 같다**(노스스타 중립문 포함). 단, vibe-flow 군에만 도구 설치 커밋의 `docs/goals/G-000-maintenance.md`(유지보수 골 템플릿)가 추가로 있었다 — 엄밀한 문서 동일성은 아니다(다음 실험에서는 양쪽에 두거나 에이전트가 만들게). vibe-flow 군에는 실험 전에 내가 도구 설치 커밋(`.claude/skills`·`.vibe-flow.json`·`G-000`·커밋 훅)만 더했고, 골 G-001·설계·MR은 에이전트가 스킬 절차로 직접 만들었다. 지시문은 같고(vibe-flow 군만 "이 흐름대로" 한 문단 추가) 시간 한도 25분, 채점기·정답 구현은 에이전트가 닿지 않는 폴더에 두었다.

- **과제 3 (버그 신고):** 월·연 경계 숙박이 0박·0원으로 청구되고, 같은 날 체크아웃·체크인이 거절된다. 원인은 `billing`(일(day) 숫자 뺄셈)과 `dates.overlaps`(`<=`) 두 파일.
- **과제 4 (기능 요청):** 장기 할인 단계(7~13박 10%·14박+ 15%), 법인 5% 추가, **할인만** 0.5원 올림. 공용 `money.won()`(파이썬 `round`, 세금·ADR에도 쓰임)을 고치면 세금·ADR이 바뀌는 회귀 함정 — 숨은 테스트가 세금·ADR 0.5 경우를 본다.

| | 숨은 테스트 | 블라인드 코드 품질(20점) | 걸린 시간 | 그 밖 |
|---|---|---|---|---|
| 과제 3 대조군 1·2 | 12/12 · 12/12 | 17 · 18 | 45초 · 47초 | 둘 다 `won()` 반올림 문제를 보고서에만 언급 |
| 과제 3 vibe-flow 1·2 | 12/12 · 12/12 | 19 · **20** | 4.8분 · 4.6분 | 2번은 `won()` 문제를 골 후보 파일로 남김. 1번은 설계 확인 생략 → 리뷰 단계에서 막힘 → 구현 뒤 설계 확인(아래 결함) |

블라인드 채점: 바깥눈(Aside ChatGPT, 추론 High)에 코드·테스트 diff만 무작위 라벨로 보냈다(기록 파일 제외). 정확성·가독성·테스트·범위 각 5점. 바깥눈은 할인·세금·청구액을 직접 검산했고 "8개 구현 모두 확정 기능 결함 없음, 운영 코드 수정 로직은 사실상 동일, 차이는 테스트 방어력"이라고 판정했다.

**결론(과제 2개 × 2회 범위에서):** 회귀 함정이 있어도 8명 모두 피했다 — 숨은 테스트로는 두 군을 가를 수 없었다. 블라인드 품질 합계는 과제 3에서 vibe-flow가 높고(39 대 35, 테스트를 더 촘촘히 씀) 과제 4에서는 같다(38 대 38). 시간은 약 5배. 이 표본으로는 "vibe-flow가 코드 정확성을 높인다"고 말할 수 없고, 관찰된 차이는 테스트 범위·골 후보 기록 같은 부수 산출물에 있다.

## 한계

- 과제 2개·반복 2회 — 작은 표본. 큰 코드베이스, UI, 여러 날에 걸친 작업은 시험하지 않았다
- 리뷰가 두 회차 모두 1라운드 무지적 — 리뷰 루프가 코드 결함을 잡는 효과는 이 실험에서 관찰되지 않았다(설계 확인은 두 번 다 실제 공백을 찾았다)
- 시간 비용이 크다(작은 일 기준 약 3~6배). 작은 변경 생략 기준(50줄·3파일)으로 설계 확인을 건너뛸 수 있지만 리뷰·QA는 그대로다

**두 번째 재실행(게이트를 실제 증거에 묶은 뒤, t3v6·t4v6):** 설계·리뷰 「확정」을 Codex 기록과 대조, 리뷰 뒤 코드 변경 재리뷰, QA는 `qa_run.py` 실행 기록, 기록 커밋에 `mr/G-001.md`·`mr/G-001-qa.json`. 두 명 모두 스크립트에 막힌 곳 없이 merge 검사까지 통과, 숨은 테스트 12/12, 3~4분. t4v6에서는 설계 확인이 major 1건(두 할인 뒤 세금 검증 테스트 누락)을 실제로 잡아 테스트 계획에 반영됐다. 드러난 결함 1건: `qa_run.py --mr`이 결과 줄을 템플릿 안내 주석 속 예시 줄 자리에 넣음(둘 다 보고) → 주석 밖에만 쓰도록 수정(RED → GREEN, `test_c2_qa.RunAndRecordTest.test_mr_option_leaves_template_comment_alone`).

**세 번째 재실행(런 5 최종 스킬, t3v7·t4v7):** 둘 다 숨은 테스트 12/12, merge 검사·`verify-evidence`까지 통과, 기록 커밋에 `mr/G-001.md`·`-qa.json`·`-review.md`. 금액 변경이라 강화 프로필이 적용돼 회귀 테스트 이름을 계획·QA에 적었다. t4v7은 설계 확인 1회차가 실제 blocker(청구서가 guest 정보를 안 가져오는 설계 공백)를 잡아 2회차에 확정. 열린 결정은 「질문·결정자·영향·기본값」 형식으로 넘겼다. 드러난 결함 2건(`goal_gate.py candidate --help`가 「--help」 후보를 만듦, lint가 `inv["discount"](합계)`를 링크로 읽음) → 실패 테스트 먼저 → 수정.
